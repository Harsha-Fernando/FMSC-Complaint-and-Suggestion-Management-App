# Interface languages

The application supports English (`en`), Sinhala (`si`), and Tamil (`ta`). The language selector sits immediately before the notification bell in the workspace navbar. It is also available on sign-in pages and in Django admin. The preference is stored in a one-year browser cookie, so it survives reloads and sign-out on that browser; it is not a cross-device account setting. Option labels always retain their native names (English, සිංහල, தமிழ்), including when Tamil is active. Unsupported choices are rejected. English is the default and fallback.

## Scope and data

Navigation, forms, validation, statuses, dashboard labels, dates, notifications generated by the application, and JavaScript feedback use Django gettext catalogs. Role permissions and workflow codes do not change with the language. User-entered complaints, suggestions, names, replies, category names and authority names stay exactly as entered. This feature does not use machine translation or send complaint content to a translation service.

New notifications store a message template and structured parameters alongside their original English snapshot. The displayed wording follows the viewer's language, without translating user text embedded in it. Historical notifications with arbitrary wording and audit descriptions retain their recorded text. Email bodies and CSV export headings remain in English. Unmatched framework or third-party administrative strings fall back to English; Django has no built-in Sinhala catalog, so project catalogs supply common framework validation and date messages through `accounts/locale_support.py` extraction anchors.

With JavaScript enabled, switching language preserves ordinary unsaved form fields and selected evidence files in transient browser memory. Passwords are excluded. No draft is written to local storage or sent to the server by the switch. A failed request leaves the current form available for retry. Native POST language selection also works without JavaScript, but a page reload cannot retain an unsaved draft in that mode. The operating system's file dialog follows its own language; the application's file-picker label and selection feedback are localized.

## Maintaining translations

Use `{% translate %}` / `{% blocktranslate %}` in templates, gettext functions in Python, and `gettext` / `interpolate` in JavaScript. Use named placeholders and plural forms; do not concatenate translated sentence fragments. Keep database identifiers and raw user content out of translation catalogs. Route new system notifications through `cases/messages.py` and `notify()`.

Catalogs are maintained in `locale/{si,ta}/LC_MESSAGES/`, separately for server messages (`django.po`) and browser messages (`djangojs.po`). English is the source language. After changing strings, install GNU gettext tools and run:

```sh
.venv/bin/python manage.py makemessages -l si -l ta --no-wrap --no-obsolete -i node_modules -i .venv -i tests -i docs -i scripts -i '*.txt'
.venv/bin/python manage.py makemessages -d djangojs -l si -l ta --no-wrap --no-obsolete -i node_modules -i .venv -i tests -i docs -i scripts
# Edit and review both languages' PO files, then compile:
.venv/bin/python manage.py compilemessages -l si -l ta -i .venv -i node_modules -i .local-checks
```

Ship the compiled `.mo` files with the `.po` sources and restart application workers after changing catalogs. The JavaScript catalog is served without caching to prevent stale language feedback after switching. Translations have automated coverage but still need native-speaker editorial review before institutional release.

## Layout and deployment

`static/css/language.css` provides flat-colour selector styling and language-specific typography. Sinhala and Tamil Noto fonts are self-hosted in `static/fonts/` with their SIL Open Font License files; no runtime external font request is needed. Text can wrap instead of relying on fixed English widths. All three languages are left-to-right. Authentication headings use a smaller Sinhala/Tamil type scale, natural letter spacing and 1.65 line height rather than English display typography. The shared sign-in/reset layout provides a 460px maximum form width and a compact single-column mobile layout. Existing translated copy is reused without changing catalog entries. Case titles and progress labels also allow script-appropriate leading and wrapping.

Apply migrations normally. `cases.0002_notification_translation_metadata` adds the two notification metadata fields without rewriting case content. The existing working database was backed up before this migration; backups remain under `.local-backups/` and should never be published.

## Verification

Backend tests cover all six roles in all three languages, translated validation, notification parameters and escaping, language preference, CSRF, safe redirects, and admin screens. Browser tests cover all six role dashboards in all three languages with automated accessibility checks, Sinhala/Tamil mobile layouts, native fallback, failed switches, persistence, and retaining text and evidence through multiple language switches followed by submission.
